# 0014. Job cards and jobs

Date: 2026-10-22 · Status: accepted

## Context
Agents ran in a free tool loop: a model chose the next tool each step, and the only limits were the pack's policies and a few lines in the prompt. That is fine for the case coordinator, but not for an agent that talks to customers or works on a fixed routine. Owners could not see what an agent was for, where it must stop, or what it would do when a customer wrote "my gas pipe is leaking". Calls to staff and outside parties were already scripts with a model only reading replies ([ADR 0007](0007-phone-delegation-to-staff.md), [ADR 0013](0013-calls-to-outside-parties.md)); written work needed the same shape. Design: [agent method](../superpowers/specs/2026-10-19-agent-method-design.md), sections 4.1 to 4.3.

## Decision
- **Every agent has a job card** (`job:` in pack YAML): a mission of up to 300 characters, a plain-words `never` list, `customer_facing`, `forbid` (tools), `escalate` (word sets) and `trial_days` and `metrics` for plan 1b. "May do" is not written; the card shows the agent's tools in plain words. Owners edit the mission, the never list and the words and alerts of each set (audited). They cannot remove an inherited set.
- **Escalation sets are pack data.** Base packs define shared sets (anger, legal threats, emergencies, distress, card and OTP secrets, each with Hindi and Hinglish forms) with `for: customer_facing`; an agent inherits them when its card says it is customer-facing, and adds its own. An own set with a shared set's id adds its words to it. Emergency and distress are `customer_facing`, not `all`, so internal safety and maintenance desks, whose work is logging accidents, are not handed every case.
- **Escalation is code.** The `escalate` check matches the listed words against the text (whole words and common endings, in Hindi script too). A hit hands the run to a person: the run ends `needs_person` (or `stopped` with `on_fail: stop`), the set's alert goes to its role (the owner when nobody holds it), the set's reply is drafted and never sent, and the audit records `job.escalated`. An escalate check must hand to a person or stop; `validateJobs` rejects `flag`, which would drop the alert and let the run act. The prompt's ESCALATE WHEN part only tells the model to call `human__handoff`; it is never the safety net.
- **Forbidden tools are policies.** Each tool in `forbid` compiles to a forbid policy for that agent (Level 5), so the policy engine refuses it whatever a model proposes. Job steps and the tool loop go through the same engine.
- **Jobs are scripts.** A job is a list of steps in pack YAML, each one `read`, `ai`, `check` or `act`. Code reads, code checks and the policy engine acts; the model only fills the typed fields of an `ai` step, parsed with zod and one repair round. With no model, an `ai` step answers from its `offline` text or hands the run to a person, and every safety behaviour comes from the checks, so it is the same with or without a key.
- **Jobs run on the existing task workflow.** `JobRunnerService` (`master-ai-backend/src/jobs/`) takes the place of the model when a task belongs to a job run: it works out the next step from the run's saved state. A run is an ordinary goal with one task, so pause, budgets, the kill switch, approvals, realtime, narration and the audit trail are the ones everything else uses.
- **Checks are a fixed set** (`escalate`, `required`, `in_data`, `limit`, `adds_up`, `within_days`, `duplicate`, `says_not`, `valid`, `calc`), worked out in `packages/agent-kit/src/jobs/checks.ts`. `calc` is parsed by a small parser, never evaluated as code.
- **Money never comes from the AI.** `validateJobs` rejects an `act` argument that moves money (`amount`, or any argument of a tool whose risk says `movesMoney`) when it uses an `ai` result, directly or through a `calc` or an earlier `act` that used one. Amounts and payment details come from records or checks.
- **Five triggers**, one per job: `request` (a case of the named categories, or `any`, arrives or reaches Execute), `schedule` (days and a time, a Temporal Schedule `job-<workspaceId>-<jobId>`), `list` (an item becomes due by an overdue or expiring rule), `record` (a record is created or changed and meets the conditions) and `manual` (Run now, with an optional text box). List and record jobs are found by one 10-minute sweep (Temporal Schedule `jobs-<tenantId>`) that runs while any such job is on.
- **Switches, caps and dedupe.** A new install has every job on; jobs that arrive later through the update banner arrive off. The owner switches each job and sets its daily cap (the pack's `daily_cap`, default 50, up to 500); runs past the cap wait for tomorrow and the owner is told once a day. Every run has a dedupe key (one per case, per item and due date, per record version, per schedule tick), checked under a lock on the job's settings. Run now ignores the switch but not a pause or the cap. Sweeps skip sample records.
- **The six-part prompt.** Every model call for an agent, from a job's `ai` step or from the tool loop, is written as ROLE, RULES and OUTPUT in the system message and TASK and DATA in the user message, with ESCALATE WHEN as the last system part. DATA sits inside the untrusted-data fence. RULES always hold the two standard lines (if the answer is not in the data, say so and ask a person; never guess numbers, dates or prices) and the card's never list; customer-facing agents also get the customer-message rule.

## Consequences
- A new kind of written work is pack YAML: a job and, at most, a new check kind in `checks.ts` with its path rules in `validateJobs`. A model never decides who is told, what is allowed or what a number is.
- `validateJobs` runs with the other pack checks (`pack.test.ts`): names must be unique and defined before use, templates may only start at `trigger`, `today` or an earlier step, and an `act` needs a tool the agent holds that its card does not forbid.
- Word matching is on word edges with a fixed list of endings (s, es, d, ed, ing, er, ers), after zero-width characters are dropped. Doubled-consonant, -ies and Hindi forms are not matched, so sets list each form. A run of `#` in a word stands for a number with that many digits, which is how the shared secrets set catches "otp 4821" and "mera pin 1234" without firing on a postal PIN code. Shared words are phrases that only turn up in a real emergency, threat or shared secret, because an installed workspace keeps them for good; the pack-content test runs must-alarm and must-not-alarm sentences through the matcher.
- No pack ships `jobs:` yet. Trial runs, test sheets and going live (plan 1b) must land first, so an agent's first runs are seen by the owner before anything leaves the company.
- Escalation replies are drafted and audited but not delivered; delivery belongs with the customer reply page (part 2).
- Cards and sets sit in the workspace's pack snapshot. Base-pack additions reach existing workspaces through the update banner, which adds and never replaces.
